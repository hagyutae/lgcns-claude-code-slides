컨텍스트

/clear 와 /compact 의 차이

/clear

  • 대화를 통째로 비웁니다. 앞에서 읽은 파일도 잊습니다.
  • 주제가 완전히 바뀔 때 사용합니다.
  • 규칙 하나를 끝내고 다음 규칙으로 넘어갈 때가 그런 경우입니다.

/compact

  • 대화를 요약해 줄입니다. 지금까지의 흐름은 남습니다.
  • 같은 작업을 이어 가야 하는데 공간이 부족할 때 사용합니다.
  • 공간이 거의 차면 요청하지 않아도 자동으로 실행됩니다.
요약에는 손실이 따릅니다.
방금 정한 규칙이나 세부 조건은 요약 과정에서 빠질 수 있습니다. 중요한 결정은 대화에만 남기지 말고 파일에 기록하세요.

권한

permissions 규칙 표기

.claude/settings.local.json  ·  자동 생성이 아니라 직접 작성하는 예시
{ "permissions": {
    "allow": ["Bash(uv run pytest:*)", "Read(docs/**)"],
    "deny":  ["Bash(git push:*)", "Edit(tests/golden/**)"]
} }
  • 규칙은 도구 이름과 대상으로 씁니다. Bash 는 명령을, Read 와 Edit 는 경로를 받습니다. deny 가 allow 보다 우선이므로 둘 다 해당하면 차단됩니다.
  • 명령 규칙의 접미사 표기: 명령 뒤에는 :* 를 붙입니다. Bash(git status *) 처럼 공백으로 적으면 인자 없이 실행한 git status 에는 규칙이 적용되지 않습니다.
도구와 경로 단위로 Agent의 활동 범위를 정할 수 있습니다.
deny 에 디렉터리나 파일 경로를 적어 두면 수정 요청이 들어와도 그 경로는 바뀌지 않습니다.

> 필수 항목이 비어 있습니다: {항목명}
  • 규칙 하나에 파일 하나: rules/r001_required_fields.py 로 만듭니다.

조립과 등록 지점

  • 조립: 규칙과 로더, 리포터 같은 구현체를 골라 서비스에 끼우는 일입니다. 이 코드를 container.py 로 모으면 나머지 코드는 구현체를 몰라도 됩니다.

from core.domain.rules.r001_required_fields import R001
from core.service.usecase.settlement import RuleBasedSettlementService

def all_rules():        # 구현한 규칙을 여기에 등록
    return [R001()]

def build_service(rules=None):
    return RuleBasedSettlementService(
        all_rules() if rules is None else rules)
